# Structured payload fixtures (payload kind 2)

These files pin down payload kind 2 of the general binary container, the structured document payload of ThreeMD
2.1 (SPEC.md section 11.3). The Swift, TypeScript and Rust ports must all reproduce the anchors byte for byte when
they write, decode them to the same `Document` when they read, and report the same error code for every vector under
its limits (SPEC 11.3.18).

The anchors were first generated by the TypeScript prototype of the ThreeMD 2.1 specification package, reproduced byte
for byte by independent Rust and Swift prototypes, and checked against the ThreeMD 2.0 bounded text decode of each port.
Nothing is generated at test time. `scripts/structured/generate.mjs` regenerates every file from the built TypeScript
library (see [Regenerating](#regenerating)).

Every committed ThreeMD 2.0 `.3mdb` file (payload kind 1) stays byte-unchanged and keeps its name. The kind-2 file
of a case sits next to it or here, never in its place.

cases. The canonical texts the prototypes used are not committed: the sources and the kind-1 anchors are already in
the repository, and each port derives the canonical text with its own writer.

## `manifest.json`

Schema `3md-structured-golden-1`. Top level: `schema`, `note`, `source` (the commit whose sources produced the
anchors), `counts` (`interchange` 49, `examples` 2, `worked` 3), `totals` (kind-2 and canonical bytes over the
interchange set) and `files`. Every path is relative to the repository root. Each entry of `files` has:

| Field | Meaning |
|---|---|
| `id` | The interchange case id, `canopy`, `shared-grove` or `worked-<name>` |
| `set` | `interchange`, `examples` or `worked` |
| `kind` | `document`, or `composition` when the anchor is the profile envelope of a composition |
| `sourceFile` | The readable source. Worked examples have none and carry `(spec 11.3.17 <name>)` |
| `textContainerFile` | The committed kind-1 file of the same case, when one exists (24 entries) |
| `extensionSourceFile` | The `conformance/extensions` source of an `extension-*` case |
| `kind2File` | The kind-2 anchor |
| `bytes`, `payloadBytes` | File size, and the payload size (`bytes - 40`) |
| `canonicalBytes` | Length of the canonical text, `T` in SPEC 11.3.7 |
| `sha256` | SHA-256 of `kind2File` |
| `crc32` | The header CRC-32, as 8 lowercase hexadecimal digits |
| `planes` | Plane count of the decoded document |
| `compositionEnvelope` | `true` for the profile envelopes |

Checks for every anchor, in every port:

1. `D` is the bounded text decode of the case's canonical text. For a composition, `D` is the profile envelope of
   the decoded composition (`DocumentCompositionCodec.document`), and the `.binary` encode runs under the profile
   limits. `encode(D, .binary(.none))` equals `kind2File` byte for byte.
2. `decode(kind2File)` equals `D`. Swift compares the `utf8` of every string and the bit pattern of every number,
   because `Document ==` treats canonically equivalent strings as equal. TypeScript uses `documentsEqual` plus
   `Object.is` on numbers. Rust uses `==`.
3. `encode(decode(kind2File))` equals `kind2File`.
4. `containerInfo(kind2File)` reports version 1, kind 2, compression 0, flags 0, reserved 0, both lengths equal to
   `bytes - 40`, and `crc32`.
5. Where `textContainerFile` exists, it decodes to `D`, and `encodeTextContainer(D)` (for a composition, of the
   envelope) equals it byte for byte.
6. A composition decoded from its envelope equals the composition decoded from the readable source.
7. The SHA-256 of the file equals `sha256`.

## `vectors.json`

Schema `3md-structured-vectors-1`, entry point `DocumentStorageCodec.decode`. Top level: `schema`, `entryPoint`,
`note` and `vectors`, listing the 142 vectors of `invalid/` and then the 14 of `limits/`. Each vector has:

| Field | Meaning |
|---|---|
| `name` | Unique vector name |
| `file` | The vector file, relative to the repository root |
| `rule` | The SPEC 11.3 step label that decides the outcome (D2, D4 to D13, V1 to V3, C, Str1 to Str4, N, S1, S2, S4, S6 to S10, S6b, P1, P7, P7a, R2, R3, R9, G1 to G6, Q, L0 to L5). For an `ok` vector it is the step whose boundary the vector sits on |
| `description` | What the bytes hold |
| `limits` | `DocumentDecodeLimits` fields to apply; absent fields are standard. Present on 29 vectors |
| `expected` | The error code a 2.1 reader reports, or `ok` when the file must decode |
| `expected20` | What a ThreeMD 2.0.0 reader reports under the same limits |
| `errorType` | `DocumentStorageError` for the 131 error vectors, `none` for the 25 `ok` vectors |
| `requiresNoLZFSE` | `true` on the one vector that only holds for readers without an LZFSE backend |
| `textValidate20` | For the 80 vectors whose bytes describe a well-formed `Document`: the outcome of the TypeScript `validate` on it (unchanged in 2.1) |

The limits decide the outcome: under standard limits, 18 of the 29 limit-bearing vectors give a different code.
Every consumer must apply them. The unit tests pass them to storage decode, the interchange driver sends them in the
request's `limits` object, and the 2.0.0 compatibility job passes them through its per-language library harness.

Every file is a complete container with its lengths and CRC resealed, unless the vector is about the container
itself. Each port decodes each vector with storage decode under its limits and must return exactly `expected`. The
Swift LZFSE backend skips the `requiresNoLZFSE` vector. Every string in the anchors and in these vectors uses only
code points assigned in Unicode 13.0 (SPEC 11.3.15); vectors that depend on newer Unicode data live in each port's
own suite.

## `sizes.json`

The input of the size gate G6 (`docs/design/threemd-2.1/perf-gate.md`, section 4): `examples` (file count, canonical and
kind-2 totals, their ratio, the number of files whose kind-2 form is smaller, and the smallest and largest per-file
ratio), `large` (synthetic-2000 and sculpt-4096) and `perFile` (canonical and kind-2 size of each of the 293
`Examples/*.3md` files).

## `numeric-powers.json`

Every signed power of two from 2^-1074 to 2^1023 (4,196 entries) and ±10^k for k from -30 to 30 (122 entries), as
`bitPattern` (the binary64 bits, big-endian hexadecimal), `formatted` (the canonical spelling of SPEC 11.3.7, as
the TypeScript writer prints it) and `name`. The 4,318 entries hold 4,316 distinct values, because +1 and -1 appear
both as 2^0 and as 10^0.

## Worked examples

All values are hexadecimal. Each example is a complete file.

### `worked-keys.3mdb`

Key byte order: version `1`, empty axis, metadata `z` = `1` and `é` = `2` where `é` is spelled decomposed (U+0065
U+0301, bytes `65 cc 81`), and one plane at `z=-3` with attributes `b` = `x` and `a` = `y`. The canonical text (67
bytes, 9 lines) lists `z` before `é`, because text uses NFC scalar order (U+007A is less than U+00E9):

```
---
3md: "1"
axis: ""
z: "1"
é: "2"
---

@plane z=-3 a="y" b="x"
```

The kind-2 file stores `é` before `z`, because its first byte `65` is smaller than `7a`. The file is 68 bytes, with
CRC-32 `0x649EB26B`:

28      1c 00 00 00 00 00 00 00                          decoded length 28

Storing the metadata keys in text order (`z`, then `é`) is `invalidContainer` (vector `order-nfc-instead-of-bytes`).
Adding the precomposed `é` (`c3 a9`) as a third key, after `z` in byte order, is `invalidDocument` at S6b, because
it is canonically equivalent to the decomposed key.

## Regenerating

`scripts/structured/generate.mjs` runs under Node or Bun with no dependency. It imports the built TypeScript
library, rebuilds every file listed in [Layout](#layout) except the Unicode table (an input), and checks each
expectation on the way: every vector gives its `expected` code under its limits, every anchor passes the checks
above, and every anchor and vector string is inside the Unicode 13.0 set.

```sh
(cd js && bun run build)                     # the library the generator imports
node scripts/structured/generate.mjs         # same as --check: compare bytes and SHA-256, write nothing
node scripts/structured/generate.mjs --write # write every output and remove structured files nobody generates
```

`--check` exits 1 and lists each missing, changed or unexpected file with both SHA-256 values. Review the change and
commit regenerated fixtures in a commit of their own; the Swift and Rust tests reproduce the same bytes
independently, so the generator is never the only source of truth. The generator exits 2 when it cannot run: when
`js/dist` is missing, or when the built library has no payload kind 2 writer (`encodeTextContainer`,
`containerInfo` and `supportedPayloadKinds` are the ThreeMD 2.1 API).

`sizes.json` also needs the two large performance-gate inputs, `synthetic-2000.3md` and `sculpt-4096.3md`
(`docs/design/threemd-2.1/perf-gate.md`, section 2). The generator reads them from `--inputs DIR`, else from
`bench/inputs`, else it runs `scripts/bench/generate-synthetic.mjs` and `scripts/bench/generate-sculpt.mjs` with Node
into a temporary directory. `--library PATH` loads another module with the same exports instead of `js/dist/index.js`.

`expected20` comes from the 2.0.0 container steps, which check the input size, the header length and the version,
and then accept payload kind 1 only; the 2.0.0 compatibility job confirms it against the real 2.0.0 readers.
