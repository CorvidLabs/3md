SpecSync change
`add-a-structured-binary-document-payload-kind-2-to-threemd-2-1-in-swift-typescript-and-rust-with-fast-checksums-cli`
(WP0) so that every reference to "test-plan section N" resolves in the repository. The section numbers are
unchanged. The package's own paths map to the repository as follows:

| `spec-11-3.md` | `SPEC.md` 1.2, sections 11 to 13 |
| `api.md` | the change's `design.md` (in `.specsync/changes/`, and in `.specsync/archive/changes/` after finalization) and `specs/ThreeMD/ThreeMD.spec.md` |

Adaptations made on copying: the opening paragraph and section 7 now say that the ThreeMD 2.0.0 compatibility job

## 1. Golden fixtures

port's 2.0 bounded text decode of the canonical text (section 11). They land in the repository as follows.

Every committed 2.0 `.3mdb` file stays byte-unchanged and keeps its name. The 45 + 4 interchange anchors and the 3
worked examples are reproduced by each port's writer; nothing is generated at test time.

**Checks per port, for every golden file:**

1. `encode(D, .binary(.none))` equals the file byte for byte, where `D` is the bounded text decode of the case's
   canonical text (for compositions, `DocumentCompositionCodec.document(for:)` of the decoded composition).
2. `decode(file)` equals `D` (Swift: compare `utf8` of every string and the bit patterns of every number, because
   `Document ==` treats canonically equivalent strings as equal; TypeScript: `documentsEqual` plus `Object.is` on
   numbers; Rust: `==`).
3. `encode(decode(file))` equals the file (P2).
4. `containerInfo(file)` reports version 1, kind 2, compression 0, flags 0, reserved 0, equal lengths of
   `bytes − 40`, and the manifest CRC.
5. Where `textContainerFile` exists: `decode(textContainerFile)` equals `D`, and `encodeTextContainer(D)` (for
   compositions, of the envelope) equals the kind-1 file byte for byte.
6. Composition envelopes: `DocumentCompositionCodec.decode(file)` equals the composition decoded from the readable
   source, and re-encoding it with `DocumentCompositionCodec.encode` gives the canonical profile text.
7. The SHA-256 of each file equals the manifest.

**Fixture generator.** `scripts/structured/generate.mjs` (Node, using the built TypeScript library) regenerates the
anchors, the vectors and `sizes.json` from the catalog and writes them only when `--write` is passed. Its output is
reviewed as a separate commit, and Swift and Rust reproduce the bytes independently, so the generator is never the
only source of truth. A CI step runs it without `--write` and fails on any difference.

## 2. Hostile, edge and limit vectors

`spec21/golden/invalid/` (142 vectors) and `spec21/golden/limits/` (14 vectors) land as
`conformance/structured/invalid/*.3mdb`, `conformance/structured/limits/*.3mdb` and one manifest,
`conformance/structured/vectors.json` (schema `3md-structured-vectors-1`, 156 vectors). Each entry has:

- `name`, `file`, `rule`: the SPEC 11.3 step that decides the outcome, always a step label (D2, D4 to D13, V1 to
  V3, C, Str1 to Str4, N, S1, S2, S4, S6 to S10, S6b, P1, P7, P7a, R2, R3, R9, G1 to G6, Q, L0 to L5). For an `ok`
  vector it is the step whose boundary the vector sits on (for example `edges-maximumDecodedBytes-at` is L4 and
  `eighty-planes-emax-1000` is L4, because L4 compares T with Dmax and nothing compares T with Emax);
- `limits` (DocumentDecodeLimits fields; absent fields are standard). 29 vectors carry `limits` and 127 do not. The
  limits decide the outcome: under standard limits 18 of the 29 give a different code (for example
  `container-decoded-over-2dmax-bad-crc` gives `checksumMismatch` instead of `oversizedOutput`, and `too-many-planes`
  decodes). Every consumer must therefore apply them: the unit tests pass them to storage decode, and the
  interchange driver sends them in the request's `limits` object (section 6);
- `expected`: the stable error code, or `ok` for a boundary vector that must decode;
- `expected20`: the outcome of a ThreeMD 2.0.0 reader under the same limits (used by section 7);
- `errorType`: `DocumentStorageError` for the 131 vectors whose `expected` is an error code and `none` for the 25
  `ok` vectors; for the LZFSE vector, `requiresNoLZFSE: true`.

Every file is a complete container with lengths and CRC resealed, unless the vector is about the container itself.
Every port decodes every vector with storage decode under the vector's limits and must return exactly `expected`.
The Swift LZFSE backend skips `requiresNoLZFSE` vectors; real LZFSE vectors for kind 2 are generated by the Swift
tests on Apple platforms (section 3).

Every `invalidDocument` and `ok` vector that encodes a well-formed `Document` was also checked against ThreeMD 2.0
TypeScript `validate`: acceptance agrees whenever the bytes are that document's canonical kind-2 encoding. The
equivalent-key vectors are the deliberate exception: 2.0 TypeScript `validate` merges such keys and accepts, while a
kind-2 payload must already hold the merged map.

**Per-port vectors (not cross-port):**

- **TypeScript writer:** lone surrogates in every string field (`invalidDocument`); equivalent keys merged (first
  spelling, last value): for metadata `{"e\u0301": "first", "\u00e9": "last"}` (written with JSON escapes because
  both keys render as "é"; the decomposed key comes first in insertion order, so its spelling is kept with the last
  value) the expected payload is `00 01 31 00 01 03 65 cc 81 04 6c 61 73 74 00`; a lone surrogate in a value that the
  merge drops (`invalidDocument`, as 2.0 `validate`); a map with the key `__proto__` round-trips as an own property.
- **Rust writer:** a `BTreeMap` with both `e` + U+0301 and U+00E9 is `invalidDocument`.
- **Swift writer:** `Document` cannot hold equivalent keys; a dictionary built from decomposed and precomposed
  literals keeps one entry.
- **Unicode skew** (11.3.15), Unicode 17 data only: U+0897 after U+0316 inside a key next to its reordered form;
  the Garay case pair U+10D50 and U+10D70 in an attribute key (R9). These code points are outside the Unicode 13.0
  set (`scripts/structured/unicode-13.0-assigned.json`), so the vectors live only in each port's own suite, with
  results recorded for Unicode 17, and never in `vectors.json` or the interchange gate. Every string in the anchors
  and in `vectors.json` is inside the set (checked by the fixture generator; verified for the spec21 goldens).

## 3. Unit tests per port

Swift (`Tests/ThreeMDTests/DocumentStorageStructuredTests.swift`), TypeScript (`js/test/structured.test.ts`), Rust
(`rust/tests/structured.rs`):

- Var encode and decode at 0, 127, 128, 16,383, 16,384, 2,097,151, 2,097,152 and 2^28 − 1, and every rejection case
  of V1 to V3.
- Number forms: `formOf` against the table of 11.3.3 for 0, −0 (written `00`), ±1, 2^27 − 1, −2^27, ±2^27, 2^24 + 1,
  0.5, 0.1, 1.5, 2^53, 2^53 + 2, 5e-324, 1.401298464324817e-45, `f32::MAX`, 1.7976931348623157e308, 2^-140, 1e15,
  1e16, 1e-7; zigzag at the range edges; decode of each encoding is bit-exact.
- CRC: check value `0xCBF43926`; the slicing loop against a bytewise reference on 10,000 random buffers of length
  0 to 300 at every alignment; the kind-1 anchors keep their CRCs.
- Swift UTF-8 rule: `String(decoding:)` plus byte equality on the Table 3-7 boundary list, including ill-formed
  inputs whose repaired length equals the input length, so that a length comparison alone would miss them:
  `F0 90 80` → `EF BF BD` (3 bytes to 3) and `F0 90 80 41` → `EF BF BD 41` (4 bytes to 4). Length-changing cases
  stay in the list: `C0 80` → two replacement characters (6 bytes) and `ED A0 80` → three (9 bytes). Measured with
  Swift 6.3.3.
- Chunked UTF-8 validation: strings of 65,535, 65,536, 65,537 and 200,000 bytes with a 4-byte scalar straddling every
  chunk boundary position; chunked and whole validation agree.
- TypeScript chunked decoding (SPEC 11.3.13), as two storage decode calls in sequence: (1) a kind-2 file whose body
  ends in `E2 82` gives `invalidUTF8`; (2) the next call, on a file whose first string (the version) starts with
  the continuation byte `AC` followed by `62`, also gives `invalidUTF8`, proving that nothing carried over from call
  (1). Call (1) uses bodies of 65,537 and 200,000 bytes (the chunked path) and, as controls, 65,535 and 65,536 bytes
  (one chunk), each followed by call (2). Measured on Node 26.10 and
  Bun 1.4.0: a decoder that streams the last chunk accepts both (`decode([61 E2 82], {stream: true})` returns `"a"`,
  then `decode([AC 62])` returns `"€b"`); splitting at scalar boundaries with non-streaming calls, or streaming with
  a flushed last chunk and a new decoder per string, reports `invalidUTF8` for both.
- Segment scanner: hand cases for G1 to G6, and agreement with the 2.0 parser on 100,000 random bodies.
- Metrics: T, Lines, DirLen and the frontmatter lengths against the real 2.0 writer on every Examples document and on
  100,000 generated documents (TypeScript and Rust; Swift on 10,000).
- Key order: byte comparison against a code point comparison and against `utf8` comparison on random keys; the
  equivalence check against `normalize("NFC")`, `nfc()` and `Set<String>`.
- Canonical number spelling (all three ports, and the Rust fix in particular): the 45 existing numeric vectors, the
  three existing tie vectors of `rust/tests/extensions.rs` 181–206 (they pass with the fix), and a new file
  `conformance/extensions/numeric-powers.json` (schema `3md-canonical-numbers-1`) with every signed power of two from
  2^-1074 to 2^1023 (4,196 values) and ±10^k for k from −30 to 30 (122 values), spelled by TypeScript. The interchange
  catalog keeps `numericVectors` at the 45 existing vectors, so the gate's request count does not grow by 4,318.
- `containerInfo`: no magic (`nil`), 8 to 39 bytes with the magic (`invalidContainer`), 40 bytes and more (raw
  fields, including a reserved kind and nonzero flags reported without error).
- `encodeTextContainer`: byte-equal to every kind-1 anchor; its error order equals the 2.0 binary writer on the 2.0
  storage tests that used `.binary`.
- Writer: W1b at `Emax` = 39 (`oversizedInput`), exact `Emax` (`ok`), `Emax − 1` (`oversizedInput`); −0 normalized
  (payload `00 01 31 00 00 01 01 00 00 01 61` for one plane `z=-0` body `a`); TypeScript `unsupportedCompression` for
  identifier 7; TypeScript and Rust `compressionUnavailable` for LZFSE after the self-check (an invalid document with
  LZFSE reports the document error).
- LZFSE (Swift on Apple platforms): kind-2 round trips; the D10 bound for compressed kind 2 is
  `min(Emax − 40, 2 × Dmax)` (a file whose uncompressed payload exceeds `Emax − 40` is `oversizedOutput` even when
  the compressed file fits); concatenated and truncated streams (`lengthMismatch`).

## 4. Differential fuzzing

All generators use fixed seeds recorded in the test and in the release receipt. A failing case is minimized and added
to `vectors.json`. CI runs the CI volume on every push; the release-candidate volume runs once on the release tip
and its counts go into `docs/evidence/release-2.1.0/fuzz.json`.

| ID | Property | Generator | CI volume | Release volume |
|---|---|---|---|---|
| P1 | Totality: every input gives a value or exactly one typed error; no crash, hang or foreign exception | Byte mutations of every anchor and of the kind-2 Examples (bit flip, byte set, insert, delete, truncate, duplicate or move a span, Var damage), lengths and CRC resealed | 10^4 per port | 10^6 per port |
| P2 | Canonical bijection: `decode(x) = D` implies `encode(D) == x` | Accepted P1 mutants | all accepted | all accepted |
| P3 | Text agreement: `decode(x) = D` implies the bounded text decode of `encode(D, .text)` under the same limits (with Emax raised to T) equals D | Accepted mutants and P6 documents | all | all |
| P4 | Cross-language outcomes: the three ports report the same code for every mutant and the same bytes on re-encode | The P1 blob replayed by Swift, TypeScript and Rust | 3 × 10^4 | 10^6 |
| P5 | Writer and reader agree: `encode(D, L)` succeeds exactly when `decode(encode(D, L), L)` succeeds, and then returns the normalized D | Generated documents | 10^4 | 10^6 |
| P6 | Equivalence with validation: `encode(D, .binary, L)` accepts exactly when the 2.1 `validate(D, L)` accepts (the 2.0 `validate` with the WP2 Rust `canonical_number` fix and the Swift frozen W set; TypeScript unchanged), and then decode equals the text decode | The edge-biased generator (W at line edges, fences, `@plane` prefixes, CR and LF placement, quotes in keys, reserved spellings, equivalent keys, integer-like and byte-order-sensitive keys such as U+FF61 and U+1F600, number boundaries, TypeScript lone surrogates) under standard limits and random lowered limits (R 1 to 120, Dmax 20 to 700, Lmax 1 to 40, Pmax 1 to 5) | 10^4 + 3 × 10^4 per port | 10^6 per port (release gate) |
| P7 | Cross-language writers: for documents with no equivalent keys and no lone surrogates, the three writers report the same code under the same limits and produce identical bytes on success | TypeScript generates a JSON corpus (numbers as bit patterns); Rust and Swift replay it | 2 × 10^4 | 2 × 10^5 |
| P8 | Number canonicality: `formOf` and the bit-exact round trip agree across ports; Rust `canonical_number` equals TypeScript | All signed powers of two, 10^k, boundaries and random bit patterns | 10^5 | 10^7 |

P4 and P7 run in the interchange step of the verify lane: the TypeScript generator writes the blob and corpus into
the driver's temporary directory, and `swift run threemd-interchange` replays them through all three adapters with a
new request kind `structuredReplay` (development protocol only). Inputs with canonically equivalent keys, LZFSE and
code points outside Unicode 13.0 are excluded from P4 and P7 (11.3.9, 11.3.15). The Unicode 13.0 set is
`scripts/structured/unicode-13.0-assigned.json` (DerivedAge 13.0: 283,506 code points in 686 inclusive ranges; spec21
`golden/unicode-13.0-assigned.json`, generated from Perl 5.34.1's Unicode 13.0.0 tables and cross-checked against
Python 3.11's Unicode 14.0.0 tables, which add exactly the 838 code points of Unicode 14.0). P7 draws string code
points only from the set. P4 excludes a mutant when any maximal well-formed UTF-8 sequence in its payload encodes a
code point outside the set; this byte scan is conservative (it can also exclude a mutant whose number bytes happen
to form such a sequence), which only lowers the count. The fixture generator uses the same file.

## 5. Limits, cancellation, memory and platform tests

- **Cancellation points** (11.3.13), each with a typed cancellation and no partial output, and the same input
  decoding identically afterwards: before entry; mid-CRC on a 64 MiB input; inside a 1 MiB scalar scan; inside the
  UTF-8 validation of an 8 MiB body (between chunks); before plane k of 65,536; in Phase L; before and after a
  Phase Q parse; mid-emission and mid-self-check on encode. Swift uses `Task` cancellation, TypeScript an
  `AbortController` aborted from a counting hook, Rust a `CancellationToken` set from a test helper.
- **Amplification:** 65,536 planes whose keys contain quotes and whose labels push every directive over R are
  rejected by L3 or L4 before any Phase Q parse; release builds finish in under 1 second and peak memory stays under
  4 times the input. The test asserts that the Phase Q parse count is 0 (a test-only counter).
- **Memory:** peak RSS (Swift and Rust) or heap (TypeScript) stays under 4 times the input for the 64 MiB worst
  cases: maximum attributes (one plane, 16 million minimal attributes cannot fit a 64 MiB Dmax, so the case is
  bounded by D10), maximum planes, and one 8 MiB body.
- **Buffer ownership:** after a TypeScript decode returns, the test overwrites the caller's buffer and checks that
  the decoded value is unchanged. Swift decodes from `Data` slices with a nonzero `startIndex`.
- **Concurrency:** Swift encodes and decodes from 32 tasks at once (the TSan job); Rust runs the same under
  `cargo test` with threads and asserts `Send + Sync` on the new types.
- **32-bit arithmetic:** `cargo test --target i686-unknown-linux-gnu --test structured` on the Linux job, which
  first runs `rustup target add i686-unknown-linux-gnu` and `apt-get install -y gcc-multilib` in the
  `swift:6.3.3-noble` container (the target's standard library, and the 32-bit C runtime and libgcc the link needs)
  and links with clang like the existing Rust step, adding `CARGO_TARGET_I686_UNKNOWN_LINUX_GNU_LINKER: clang` next
  to the x86_64 and aarch64 linker variables (WP7 adds these steps to `linux.yml`); a compile-only
  `xcodebuild -scheme ThreeMD -destination 'generic/platform=watchOS' ARCHS=arm64_32 build` on the macOS perf job;
  Swift unit tests drive the Count check with `Int32` values near `Int32.max`. (A watchOS simulator cannot run
  arm64_32.)
- **Linux:** the full suites run in the existing `linux.yml` container (Swift 6.3.3, Node 24, Bun 1.4.2, Rust 1.95).

## 6. Interchange gate (`3md-interchange-2`)

**Protocol (`conformance/interchange/PROTOCOL.md`).**

- The schema becomes `3md-interchange-2`. `bytesHex` may hold text, kind 1 or kind 2.
- Document and composition requests gain an optional `limits` object:
  `{"schema":"3md-interchange-2","kind":"document","bytesHex":"...","limits":{"maximumPlanes":1}}`. It holds the five
  DocumentDecodeLimits fields (`maximumEncodedBytes`, `maximumDecodedBytes`, `maximumLines`, `maximumPlanes`,
  `maximumRecordBytes`) with exactly the shape and integral-number validation of the files request's
  `documentLimits`: each present field is an integral JSON number of magnitude at most 2^53 − 1; an absent object or
  field keeps the standard value and `{}` means standard limits; a value that is not an object (including `null`), an
  unknown field or a non-integral number gives `adapterFailure`; a value the library refuses gives `invalidLimits`.
  A request may hold only `schema`, `kind`, `bytesHex` and, for document and composition requests, `limits`; any
  other key, or `limits` on a files request, gives `adapterFailure`. Adapters check strict JSON, then the envelope
  and the `limits` shape, then the hexadecimal, then call the library, as for files requests.
- The adapter applies `limits` to the decode of `bytesHex` only: `DocumentStorageCodec.decode(bytes, limits)` for a
  document request, and the `documentLimits` argument of `DocumentCompositionCodec.decode` for a composition request
  (composition limits stay standard). Every producer encode, the adoption and edit steps, and every re-import of a
  produced output use standard limits, as the files cases already do for produced bundles. Running the producers
  under the request's limits cannot work for boundary vectors: measured on the spec21 vectors, 4 of the 7
  limit-bearing `ok` vectors would then fail (`eighty-planes-emax-1000` and `edges-maximumEncodedBytes-at` have
  canonical text and kind-1 output over `Emax`, and adoption adds `3md-id` attributes that push
  `edges-maximumRecordBytes-at` over R and `edges-maximumDecodedBytes-at` over Dmax). Writer acceptance under
  lowered limits is covered by P5 and P6, not by the gate.
- Responses:
  - `binaryHex` is `encode(.binary(.none))` for documents, and the `.binary` encoding of the profile envelope under
    the profile limits for compositions and files (kind 2);
  - new `textContainerHex` is `encodeTextContainer` of the same document or envelope (kind 1, the 2.0 bytes);
  - `canonicalHex`, `legacyHex`, `rawCanonicalHex`, `revisionHex`, `adoptedHex`, `editedHex`, `staleRejected` and

- New request kind `structuredReplay` (P4, P7): `bytesHex` holds a length-prefixed blob or a JSON corpus; the
  response holds one outcome line per item. Development only.

## 7. ThreeMD 2.0.0 compatibility job

A job in `.github/workflows/linux.yml` (and the Fledge task `compat-2-0`, which is not part of the verify lane, because
it builds a second copy of all three libraries and adapters) checks out tag `v2.0.0`
into a separate worktree and runs two parts. It proves that 2.0 readers stop at the payload kind, before the CRC
(`container-kind-3-bad-crc` and every kind-2 vector with a corrupt CRC still report `unsupportedPayloadKind`), and
that a file over the reader's `Emax` stops earlier with `oversizedInput`.

1. **Through the v2.0.0 adapters.** The job builds the three v2.0.0 interchange adapters and sends them the 54
   kind-2 anchors and the 127 limit-free vectors. The 2.0 adapters speak only `3md-interchange-1` (the TypeScript
   adapter accepts exactly the keys `schema`, `kind` and `bytesHex` and that schema), so these requests use schema
   `3md-interchange-1` and carry no `limits`. Each anchor goes as a document request, and the composition-envelope
   anchors (`composition-empty-root`, `composition-shared-dag-unused`, `extension-composition-instances`,
   `shared-grove`) also as composition requests. Every 2.0 adapter must return `unsupportedPayloadKind` for each
   anchor and the vector's `expected20` for each vector.
2. **Through the v2.0.0 libraries, with limits.** The 29 limit-bearing vectors cannot go through the 2.0 adapters,
   which have no way to receive limits. A small per-language harness, built against the v2.0.0 libraries in the same
   worktree, calls storage decode with each vector's limits and prints one outcome code per vector:
   `scripts/compat/decode-2-0.mjs` (imports the worktree's built `js/dist/index.js`), `scripts/compat/rust/` (a
   crate whose `threemd` path dependency the script points at the worktree's `rust/`, with no other dependency), and
   `scripts/compat/swift/` (a package with a path dependency on the worktree). The script turns `vectors.json` into
   a line-oriented input (name, file, the five limit values) so that no harness needs a JSON library. The harnesses
   run all 156 vectors under their limits (the limit-free ones a second time, cheaply), and every outcome must equal
   `expected20`.

Under standard limits, 28 of the 29 limit-bearing vectors still give their `expected20` (`unsupportedPayloadKind`);
only `edges-maximumEncodedBytes-below` (`oversizedInput` at `Emax` = 146) depends on the limits, which is why part 2
exists. The prototypes confirmed `expected20` by calling the 2.0.0 libraries directly, which is the method of part 2:
TypeScript and Rust for all 156 vectors, Swift for 155 (its prototype skips the LZFSE vector on macOS). All three
2.0.0 adapters map a storage error inside composition decode to the storage code (Rust: `Storage(e)` reports
`e.code()`), so the composition requests of part 1 also expect `unsupportedPayloadKind`.
